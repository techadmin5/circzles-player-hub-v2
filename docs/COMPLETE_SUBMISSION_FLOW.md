# Complete competitive video submission flow

The existing Cloudinary, video_uploads, submissions, submission_reviews, first-completion reward grants, game events and personal-best systems are reused. No new migration is required. No production import, reset, mutation, migration, merge or deployment was performed for this branch.

## Player and reviewer workflow

My CircZles detail links to Submit Attempt with the selected puzzle. The composer loads owned puzzles, displays level/current maximum, and instructs the player to record continuously from unboxing through the completed solution. The player selects their own MP4, MOV, WebM or M4V recording. Browser metadata provides local duration/preflight feedback; it is never trusted by the backend. File size is consistently capped at 104857600 bytes (100 MiB, labelled 100 MB with MiB clarification). Actual provider bytes are checked independently.

Signed uploads transfer directly from browser to Cloudinary in 6 MiB chunks, with Content-Range and a stable X-Unique-Upload-Id. Videos never pass through Next.js, Render or PostgreSQL. Progress, errors and retry are shown. Database finalization can be retried without retransferring a completed upload. Expired authorization requires reselecting the recording. Submission retries retain the same idempotency key; a lost browser response cannot create a second attempt. Success is shown only after the submission database response, with the requested Submission Received dialog and two destination links. The 24-hour review target is informational.

Submissions list/detail and CircZles history show own attempts, dates, status and review note. History supports loading/error/retry/refresh. Reviewer controls replace the previous placeholder: status filters, player identity, puzzle/level, completion time, verified duration, current maximum, size, protected viewing, approve/reject/request resubmission, optional notes and immutable decision/reviewer/timestamp history.

## Authoritative eligibility and timing changes

Creation and approval use the same validator. Upload must be COMPLETE, owned by the submitter, Cloudinary-backed, supported MIME, positive verified size <=100 MiB, and have a verified positive integer duration. Both duration and reported completion must be <= the current positive configured puzzle maximum. NULL blocks competitive submission and approval with a clear configuration message. Equality at 05:00 is accepted; 05:00.001 is rejected. The global PostgreSQL integer completion limit remains unchanged.

The backend independently fetches the controlled asset at finalization, submission creation and approval. It verifies public_id, authenticated delivery type, video resource type, allowed format, bytes, positive duration, actual video codec and positive top-level width/height (rejecting audio-only files). Duration seconds are conservatively rounded UP to integer milliseconds: a sub-millisecond excess cannot round down into eligibility. Missing metadata, incomplete processing, deleted/broken/changed assets fail safely. Creation/approval compare provider size/duration against stored verified values. No duration or asset ID supplied by a player can substitute that proof.

Pending attempts are revalidated against the current maximum at approval, serialized with catalog timing saves under the existing catalog advisory transaction lock. Tightening or clearing a maximum can block pending approval; reviewers can reject/request resubmission. Previously approved attempts, personal bests and rewards are not retroactively invalidated. Exact retries of completed creation/review return the original result even if policy later changes. Approval events include the maximum and verified video duration used for the decision. A future noncompetitive/practice mode is separate and is not implemented here.

Only approval triggers existing reward/best-time processing. First completion uses the unique player/puzzle grant; subsequent approvals cannot repeat XP/SP. Disabled rewards produce a zero-reward snapshot, without an empty database update. Rejection/resubmission and upload/submission never grant approval rewards. submission.created remains available for future First Submission missions; no mission or reward was configured here. Existing best-time ordering is retained.

## Cloudinary access and production prerequisites

New signed uploads bind authenticated delivery, overwrite=false and allowed_formats. Authenticated originals/derivatives are not publicly deliverable. Authorized SUBMISSIONS_REVIEW callers may obtain a five-minute private_download_url; it is not included in general player APIs or logs. The reviewer can play or open the original in a new tab, and renew expired viewing access. Protected download delivery uses Cloudinary API bandwidth; browser playback still depends on the uploaded codec. See [Cloudinary protected media](https://cloudinary.com/documentation/control_access_to_media) and [signed upload reference](https://cloudinary.com/documentation/image_upload_api_reference).

Cloudinary account capacity has NOT been verified against the live production Console, and no live test upload was created. Before release, the account owner must verify that maximum video upload size is at least 104857600 bytes, authenticated video uploads and protected download delivery are permitted, and quota/rate limits are sufficient. Chunking avoids the single-request limit, but cannot bypass an account limit. Account size limits are plan/configuration dependent: [Cloudinary upload limits and manual chunking](https://cloudinary.com/documentation/upload_images). Upgrade/adjust the account if necessary; the application does not silently reduce the required 100 MiB support or fall back to public delivery. Existing credentials are reused; no environment variables were changed.

Historical assets uploaded using public delivery, missing verified duration/size, or non-Cloudinary provider values cannot receive a new approval or protected viewing through this path. Existing approved data is untouched. The business must decide whether any historical pending public assets should be migrated/reverified in a separate authorized operation or requested as a new protected upload. This branch performs neither a historical migration nor an insecure public fallback.

## Cleanup and reliability

Selecting another recording requests deletion of the unused previous upload. The server rechecks owner and absence of any submission under the same management lock, rejecting deletion of submitted recordings. Finalization uses compare-and-set SIGNED/nonexpired transitions; stale failures/expiration cannot downgrade COMPLETE.

For abandoned tabs/orphaned uploads, `node --import tsx src/operations/cleanupAbandonedVideos.ts` from backend defaults to a read-only dry run. A separately authorized `--apply` removes at most 100 owned Cloudinary assets whose authorization expired more than 24 hours earlier and have no submission. Each asset is rechecked transactionally before deletion. Removed uploads remain EXPIRED with ABANDONED_REMOVED, so future batches skip them. Partial/provider deletion failures roll back the database transition and can be retried; any externally missing asset fails later verification safely. This command is not scheduled or run automatically and was not executed against production. No video attached to a valid submission is eligible for cleanup.

## Validation

Regression suites exercise size/duration boundaries, provider metadata/identity/type protection, missing timing, forbidden ownership, idempotency/upload reuse, external verification at approval, exactly-once rewards, disabled rewards, personal bests, single decisions, finalization retry/expiration and cleanup. Frontend tests exercise preflight, direct chunk progress, verification retry, lost submission response, confirmed success modal, history recovery and review controls. Full validation counts/results are recorded in the delivery report.

Final validation: backend `npm test -- --maxWorkers=2` passed 925 tests across 47 files. Frontend `npm test` passed 204 tests. Backend/frontend lint, typecheck and production builds passed, including 45 generated Next.js pages. `git diff --check` passed. Provider transport was mocked for regression tests; no production upload, review, deletion, cleanup command or data mutation was performed.
